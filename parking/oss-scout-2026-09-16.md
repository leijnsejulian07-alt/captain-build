# Captain OSS scout — 2026-09-16

Purpose: fresh candidate scan for reusable subsystems behind Captain. This is research/parking only; no third-party code was installed or executed.

## Highest-value new candidate: Vercel Open Agents

Repository: vercel-labs/open-agents
License: MIT (per upstream repository)
Observed 2026-09-16: ~5.8k stars / ~756 forks in current GitHub search snapshot.

Why it matters:
- Separates the durable agent workflow from the sandbox VM. This maps well to Captain's single-control-plane requirement: Captain can remain the orchestrator while a sandbox remains an execution environment rather than becoming a second router.
- Durable multi-step background runs, cancellation and stream reconnection are directly relevant to Captain's persistent job UX.
- Snapshot-based sandbox resume, repo cloning/branches, preview ports, optional commit/push/PR flow are useful references for OpenBuilder's plan→build→test→review/debug→preview loop.
- The architecture explicitly keeps model/provider and sandbox choices independently replaceable.

Integration fit: HIGH as architecture/reference; MEDIUM as a direct subsystem because its durable workflow and sandbox path is Vercel-centric and can imply cloud/provider cost. Prefer adapting its separation-of-concerns and lifecycle contracts rather than importing a second control-plane. Never silently enable paid Vercel resources.

Security/auth notes: GitHub support uses an official GitHub App/OAuth setup and explicit secrets. That fits Captain Settings' canonical auth model, but Captain must own readiness/permissions/remediation and never copy secrets into project state or logs.

Laptop cost: direct cloud deployment moves sandbox compute off the laptop, but adds network/provider dependency. Local Captain should remain usable without it.

## New candidate: Rivet sandbox-agent

Repository: rivet-dev/sandbox-agent
Observed 2026-09-16: active repository (~426 commits in current snapshot).

Why it matters:
- Runs inside a sandbox and exposes coding-agent sessions over HTTP.
- Supports multiple mature coding agents (upstream currently lists Claude Code, Codex, OpenCode, Cursor, Amp and Pi), which could let Captain/OpenBuilder use one narrow adapter contract instead of hard-wiring one coding agent.
- Streaming events, permissions and session management align with the desired builder pane and Captain-owned approval boundary.

Integration fit: HIGH for a future optional coding-agent transport adapter, provided Captain remains the only router/control-plane and every session/operation is wrapped in chat_id + project_id + repo_scope + epoch authority.

Security/resource notes: do not expose the HTTP control surface broadly; require loopback/private sandbox networking, explicit permission mediation, version pinning and capability allowlists. Audit license/dependencies and exact auth defaults before any prototype. No install in this scout.

## Candidate re-check: sandboxd

Still promising for local/self-hosted preview/sandbox infrastructure: API-first, Docker/Traefik/SQLite, live preview, files/diffs and idle sleep. Upstream explicitly describes it as beta/0.x and warns that container isolation is not VM isolation and API auth is off by default. Therefore it remains prototype-only until pinned, hardened and wrapped by Captain-owned authorization.

## UI/reference candidate: OpenAgentd

Interesting patterns rather than a replacement control-plane: visible tool-call inspector, inline diffs, workspace-aware coding mode, git worktrees, persistent editable memory, per-session model visibility and local telemetry. Avoid importing its own multi-agent orchestration/router wholesale; selectively reuse UI/interaction ideas if license/dependency review passes.

## Community signal

A recent r/AI_Agents discussion described a useful verification pattern: deploy an agent's changes to an ephemeral E2B/Daytona sandbox, exercise the resulting endpoints, and only then open a PR. Treat this as anecdotal design input, not authoritative evidence. The pattern reinforces Captain's desired build→test→preview→review gate and disposable-sandbox cleanup.

## Decision / priority

1. When B310 returns, reconcile and locally verify existing Captain parking work before adding any new runtime dependency.
2. Prototype a Captain-owned `SandboxProvider` boundary rather than binding OpenBuilder directly to one vendor. Required identity: chat_id, project_id, repo_scope, epoch, builder_session_id; required operations: create/resume/snapshot/exec/preview/diff/destroy; all mutation calls require one-shot Captain authority receipts.
3. Use Vercel Open Agents as the strongest architecture reference for durable-agent-vs-sandbox separation.
4. Evaluate Rivet sandbox-agent behind that boundary for multi-coding-agent transport.
5. Keep sandboxd as a local/self-hosted provider candidate, with explicit hardening requirements.
6. Do not install or execute any candidate until license/dependency/security review and local acceptance tests can be performed.
