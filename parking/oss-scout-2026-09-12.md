## Builder candidates refreshed today

### Open Builder (`Amery2010/open-builder`)
- Desktop-first AI web-app generator with a tool-call file loop and live preview via Sandpack.
- Native OpenAI/Anthropic/Google plus OpenAI-compatible endpoints; local/Tauri runtime can expose stdio MCP while web/mobile intentionally omit local process/Skill script execution.
- High fit for Captain's interactive builder pane because files + preview are already first-class concepts.
- Integration posture: keep existing Captain/OpenBuilder bridge as the primary builder baseline. Reuse/adapter only; Captain owns project memory, authorization, routing, task lifecycle and rollback authority.
- Source: https://github.com/Amery2010/open-builder

### Freebuff / Codebuff (`CodebuffAI/freebuff`)
- Apache-2.0 TypeScript/Bun monorepo; parallel local agents, browser research/testing, hosted sandboxes/previews and an embeddable `@codebuff/sdk` multi-agent framework.
- Strong candidate for an optional repo-aware multi-agent coding backend behind Captain rather than a replacement UI/control-plane.
- Privacy/cost posture: do not silently use hosted Freebuff/Codebuff services or models; hosted flows process prompts/traces/code/repository data and may show model-specific data-use notices. Prefer local/runtime/SDK evaluation first.
- Source: https://github.com/CodebuffAI/freebuff

### OpenCode (`anomalyco/opencode`)
- Active provider-neutral coding agent with separate read-only `plan` and full-access `build` modes, subagents, desktop/CLI support and Windows packaging.
- Strong reference/adapter candidate for repo exploration, planning and provider-neutral coding sessions.
- Large surface area and its own agent/session authority mean direct embedding must be bounded; do not let it own Captain Project State or persistent memory.
- Recent issue activity also shows desktop/MCP and filesystem-watch edge cases; treat process/file watcher resource cost as something to measure on the user's Windows laptop before enabling it persistently.
- Source: https://github.com/anomalyco/opencode

### Cline
- Keep as a secondary SDK/MCP/IDE-agent candidate for comparison with Freebuff/OpenCode. Do not add another always-on control-plane merely to gain MCP or coding loops Captain already has/plans.

## Selection direction
1. **OpenBuilder remains the current integration baseline** because Captain already has a bridge and regressions around it; do not throw away verified local work for a fashionable replacement.
2. Prototype **Freebuff/Codebuff as a bounded optional coding backend** when local reconciliation is possible; its SDK is the most promising route to extra multi-agent implementation/review capacity without replacing Captain's UI.
3. Prototype **OpenCode as a bounded repo/plan/build adapter** only after defining a strict capability boundary, process lifecycle and resource budget.
4. Compare Cline only where its SDK/MCP/IDE capabilities offer a measurable advantage over the above.
5. Shared interface should expose capabilities such as plan, read-files, propose-diff, apply-in-worktree, test, review, preview, console and rollback request. Captain remains authoritative for scope, memory, permissions, dispatch, state epoch, audit and user-visible result.

## Security / laptop constraints
- Never blindly run repository-provided scripts during candidate detection.
- No OAuth/API key may be invented or copied into candidate config automatically.
- No paid/hosted provider is activated without explicit user authorization.
- Third-party builder sessions must be short-lived and revocable on epoch change/repo rebind.
- Prefer isolated worktrees/sandboxes over direct writes to the active repository.
- Measure idle RAM/CPU, watcher count, startup time and disk/cache growth before allowing persistent background processes.
