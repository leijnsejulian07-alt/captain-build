## Builder candidates refreshed today

### Open Builder (`Amery2010/open-builder`)
- Desktop-first AI web-app generator with a tool-call file loop and live preview via Sandpack.
- Native OpenAI/Anthropic/Google plus OpenAI-compatible endpoints; local/Tauri runtime can expose stdio MCP while web/mobile intentionally omit local process/Skill script execution.
- High fit for Captain's interactive builder pane because files + preview are already first-class concepts.
- Integration posture: keep existing Captain/OpenBuilder bridge as the primary builder baseline. Reuse/adapter only; Captain owns project memory, authorization, routing, task lifecycle and rollback authority.
- Source: https://github.com/Amery2010/open-builder

### Freebuff / Codebuff (`CodebuffAI/freebuff`)
- Apache-2.0 TypeScript/Bun monorepo; parallel local agents, browser research/testing, hosted sandboxes/previews and an embeddable `@codebuff/sdk` multi-agent framework.
- Strong candidate for an optional repo-aware multi-agent coding backend behind Captain rather than a replacement UI/control-plane.
- Privacy/cost posture: do not silently use hosted Freebuff/Codebuff services or models; hosted flows process prompts/traces/code/repository data and may show model-specific data-use notices. Prefer local/runtime/SDK evaluation first.
- Source: https://github.com/CodebuffAI/freebuff

### OpenCode (`anomalyco/opencode`)
- Active provider-neutral coding agent with separate read-only `plan` and full-access `build` modes, subagents, desktop/CLI support and Windows packaging.
- Strong reference/adapter candidate for repo exploration, planning and provider-neutral coding sessions.
- Large surface area and its own agent/session authority mean direct embedding must be bounded; do not let it own Captain Project State or persistent memory.
- Process/file watcher resource cost must be measured on the user's Windows laptop before persistent enablement.
- Source: https://github.com/anomalyco/opencode

### Cline
- Keep as a secondary SDK/MCP/IDE-agent candidate for comparison with Freebuff/OpenCode. Do not add another always-on control-plane merely to gain MCP or coding loops Captain already has/plans.

## Sandbox / execution candidates added today

### AgentBox (`madarco/agentbox`)
- MIT-licensed sandbox/checkpoint layer that can place Claude Code, Codex or OpenCode in separate local Docker or remote boxes, with per-box browser/VS Code and snapshot/checkpoint support.
- Particularly relevant architecture pattern: git credentials stay on the host; provider plugins are explicit trust boundaries; backend compatibility is contract-tested.
- Good candidate for ideas or a bounded sandbox adapter, not for becoming Captain's orchestrator. Cloud providers must remain opt-in and cost-gated.
- Caveat: provider plugins execute as trusted host code, so Captain must never auto-install arbitrary AgentBox plugins.
- Sources: https://github.com/madarco/agentbox and its provider-plugin documentation.

### `boldblackai/harness`
- Lightweight container wrapper around several coding agents including OpenCode, with dropped capabilities, `no-new-privileges`, project-only mounts and supply-chain verification claims.
- Useful security/reference candidate for the local execution boundary because it is narrower than a full second agent platform.
- Keep as reference/optional adapter only; do not auto-mount global skills/context across unrelated Captain projects without scope filtering.
- Source: https://github.com/boldblackai/harness

### `tastyeffectco/sandboxd`
- MIT self-hosted app-builder/sandbox project with isolated Docker workspaces and preview URLs.
- Interesting for preview-environment patterns, but currently 0.x; its own documentation warns that API auth is off by default and container isolation needs hardening for untrusted multi-tenancy.
- Therefore reference-only for now; not preferred over the already integrated OpenBuilder path or a hardened Captain-owned local sandbox boundary.
- Source: https://github.com/tastyeffectco/sandboxd

### AgentFence (`balyakin/agentfence`)
- Community project using temporary shadow workspaces, pre/post secret scanning, redacted diffs and explicit patch application; supports multiple coding agents including OpenCode.
- Useful pattern for Captain's future preflight/postflight safety checks, but its Linux bubblewrap path is not directly portable to the user's Windows laptop.
- Research/reference candidate only until source/security/maintenance are audited further.

## Selection direction
1. **OpenBuilder remains the current integration baseline** because Captain already has a bridge and regressions around it; do not throw away verified local work for a fashionable replacement.
2. Prototype **Freebuff/Codebuff as a bounded optional coding backend** when local reconciliation is possible; its SDK is the most promising route to extra multi-agent implementation/review capacity without replacing Captain's UI.
3. Prototype **OpenCode as a bounded repo/plan/build adapter** only behind the same Captain dispatch boundary and with a strict process/resource budget.
4. Use **AgentBox/Harness patterns** to strengthen isolated execution, credential separation, checkpoints and provider-plugin trust boundaries; do not install them blindly or introduce their orchestration as a second authority.
5. Compare Cline only where its SDK/MCP/IDE capabilities offer a measurable advantage over the above.
6. Shared builder interface should expose bounded capabilities such as plan, read-files, propose-diff, apply-in-worktree, test, review, preview, console and rollback request. Captain remains authoritative for scope, memory, permissions, dispatch, state epoch, audit and user-visible result.

## Security / laptop constraints
- Never blindly run repository-provided scripts during candidate detection.
- No OAuth/API key may be invented or copied into candidate config automatically.
- No paid/hosted provider is activated without explicit user authorization.
- Third-party builder sessions and dispatches must be short-lived/revocable on epoch, repository, session or canonical Settings state changes.
- Prefer isolated worktrees/sandboxes over direct writes to the active repository.
- Keep credentials on Captain/host side wherever possible rather than injecting broad credentials into builders/sandboxes.
- Measure idle RAM/CPU, watcher count, startup time and disk/cache growth before allowing persistent background processes.

## Implementation note from this run
A bounded Captain builder-backend dispatch boundary is now parked on the continuity branch. OpenBuilder is the default embedded adapter; Freebuff and OpenCode are optional allowlisted adapters. Dispatch requires the current Captain builder session, exact project/repo/epoch scope, canonical Settings Installed/Enabled/Ready state plus a Settings state digest, and explicit approval for optional, remote and paid execution. Validation re-checks the current Settings digest/readiness so disabling or reconfiguring a backend revokes an already issued dispatch rather than leaving ambient authority alive until session expiry. The dispatch projection stores no credentials, prompts, model IDs or repository paths.
