# Captain OSS scout — 2026-09-14

Scope: only candidates that can sit behind Captain's existing control-plane. No third-party code was installed or executed.

## OpenHands Software Agent SDK
- Source: https://github.com/OpenHands/software-agent-sdk
- License: MIT. Active as of 2026-09-12; Python + TypeScript + REST APIs, local or ephemeral Docker/Kubernetes workspaces.
- Fit: strong optional coding-agent/builder adapter or reference implementation. Captain must remain the authority for project/repo/epoch scope, memory, routing and approvals rather than delegating control-plane ownership.
- Caution: current upstream issues include sandbox/webhook lifecycle failures and requests for more durable long-running execution. Treat Captain's own durable jobs/recovery fences as authoritative rather than assuming upstream durability.
- Decision: keep as a high-value adapter/reference candidate; do not replace Captain/OpenBuilder by default.

## kubernetes-sigs/agent-sandbox
- Source: https://github.com/kubernetes-sigs/agent-sandbox
- License: Apache-2.0.
- Fit: credible future remote/cluster sandbox adapter and useful isolation API reference.
- Cost: Kubernetes is far too heavy for Captain's normal laptop runtime, so this is not a default local dependency.
- Caution: warm-pool/claim concurrency bugs have been reported in 2026; Captain would still require its own exact session/epoch ownership fences.
- Decision: architecture/reference candidate only unless a remote cluster-backed mode is explicitly added later.

## Daytona / open continuation
- Daytona's public OSS trajectory changed in 2026; community continuation Nightona advertises itself as a fork of the last AGPL-3.0 release.
- Fit: sandbox lifecycle ideas remain useful, especially explicit readiness waiting/timeouts and pre-execution governance.
- Caution: maintenance provenance and AGPL obligations make the community fork a poor default integration for Captain today.
- Decision: do not integrate now; reuse lifecycle/governance ideas in Captain's adapter contracts.

## PlugMem
- Source: https://github.com/TIMAN-group/PlugMem
- License: Apache-2.0. ICML 2026 project; public repository created 2026-02-09, updated 2026-09-11, 299 stars at review time.
- Capability: task-agnostic long-term agent memory that distills interaction history into reusable knowledge units, with coding-agent plugin integrations published in 2026.
- Fit: potentially useful behind Captain's memory layer as an optional retrieval/distillation engine, especially if it can reduce context cost without becoming authoritative storage.
- Isolation requirement: Captain Project Memory remains the source of truth. Any adapter must inject chat_id/project_id/repo_scope/state_epoch metadata externally and fail closed before retrieval; no raw cross-project memory pool is acceptable.
- Resource cost: Python-based and much lighter than a cluster sandbox; still needs local benchmarking for index size, retrieval latency and idle memory before laptop use.
- Decision: promising evaluation candidate only. Do not integrate until local isolation, provenance, deletion and deterministic-recall tests are written.

## context-mode
- Source: https://github.com/mksglu/context-mode
- Repository state: actively updated 2026-09-14, TypeScript, about 22.7k stars at review time.
- Capability: keeps large tool outputs outside the model context, indexes session events in SQLite/FTS5 and retrieves compact relevant state; supports multiple agent clients via MCP/hooks.
- Fit: its output-sandboxing and selective-recall pattern is highly relevant to Captain's context efficiency and observability. The architectural idea is preferable to dumping raw browser/GitHub/log output into model context.
- License: GitHub reports `NOASSERTION` / Other, so direct code integration is blocked until the actual license terms are manually reviewed and confirmed compatible.
- Control-plane requirement: do not add its router/hook layer as a second Captain router. If adopted later, only use a narrow storage/filter adapter behind Captain's existing authority and epoch walls.
- Decision: study the architecture; no direct dependency or copied code while licensing remains unclear.

## Design takeaway
Captain should keep sandbox providers behind one narrow workspace adapter with explicit states: provisioning -> ready -> busy -> stopping -> stopped/failed, bounded readiness deadlines, exact project/repo/epoch/builder-session ownership, and pre-execution review/secret scanning before untrusted generated code enters any sandbox. Provider-specific retries or lifecycle quirks must never weaken Captain's own ownership and stale-generation fences.

For memory/context, keep Captain's scoped Project Memory authoritative and treat external engines only as replaceable retrieval/distillation adapters. Large tool outputs should be stored as scoped artifacts with provenance and summarized/retrieved on demand rather than injected wholesale into chat context. Any adapter must preserve exact project/repo/epoch ownership and must not introduce a second router, daemon authority or implicit shared memory pool.
