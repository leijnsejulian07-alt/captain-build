# Captain OSS scout — 2026-08-31

## OpenHands
- Capability: mature coding-agent platform with SDK, CLI, local GUI/API, agent server, evaluation tooling and extension ecosystem.
- License: core OpenHands and agent-server are MIT; enterprise directory has a separate commercial/source-available license.
- Maintenance: active project with 100+ releases; current public repo activity remains substantial in 2026.
- Integration fit: potentially valuable as an optional coding-agent backend/subsystem behind Captain, not as a second user-facing control-plane.
- Security/architecture note: only consider an adapter that preserves Captain's own chat_id + project_id + repo_scope gates, permission model, bounded execution and acceptance checks. Do not inherit a broad agent permission bucket.
- Laptop cost: likely materially heavier than the current lightweight Captain runtime, especially with Docker/browser/sandbox services; evaluate SDK/agent-server integration before full platform deployment.
- Decision: promising, but pending local resource/security evaluation. Do not install blindly.

## MCP Apps / official MCP Registry
- Capability: MCP Apps is an official MCP extension for interactive tool-returned UI; the official MCP Registry is a standard discovery source for MCP servers.
- Integration fit: strong candidate for future optional plugin/UI adapters while keeping Captain Settings as the canonical enable/connect/permission surface.
- Security note: registry discovery must never imply trust or auto-install. Require allowlisting, license/source review, explicit permissions and connector health checks before activation.
- Laptop cost: protocol/client support can be lightweight compared with embedding whole agent platforms.
- Decision: prioritize a small compatibility audit after current reconciliation work; do not add another router/daemon.

## Browser-use
- Capability: MIT-licensed browser-agent library; can reuse real browser profiles and supports local models/providers.
- Risk/cost: Chromium is memory-heavy and parallel agents can be expensive on a laptop. Authentication/session handling needs especially strict permission boundaries.
- Decision: useful future optional browser adapter, lower priority than reconciliation and project isolation. Never use stealth/CAPTCHA bypass as a default Captain capability.

## Limboo
- Capability: active MIT-licensed desktop orchestrator with per-session git worktrees, integrated terminal/filesystem, local memory, resume pipeline, MCP layer and OS-level sandboxing.
- Integration fit: strongest value is architectural reuse/reference for the interactive builder pane and isolated coding-session UX, not replacing Captain's router or user-facing shell.
- Security/maintenance: recent v1.7.0 and documented hardened IPC are positive; published builds are currently unsigned, so no binary install should occur without source/build review.
- Laptop cost: Electron plus multiple local agent sessions can be material; selectively adapt worktree/session ideas before considering runtime embedding.
- Decision: promising design/reference candidate; pending code/license/dependency audit.

## Bothread
- Capability: local MCP-native multi-agent coordination with file claiming/collision prevention, human visibility and no model/API-key layer of its own.
- Integration fit: potentially useful as a lightweight coordination adapter behind Captain's repo-aware build loop, especially for preventing parallel agents from editing the same files.
- Security/architecture: because it coordinates rather than routes models, it can fit the single-control-plane rule if Captain remains authority for project/repo scope and permissions.
- Laptop cost: likely modest relative to full sandbox stacks, but requires local validation of process/MCP behavior.
- Decision: high-interest candidate for a narrow adapter or concept reuse; do not run unreviewed code.

## SideButton
- Capability: open-source MCP server plus Chrome extension, browser workflow engine, knowledge packs, git/shell steps and dashboard.
- Integration fit: browser/workflow capability is broad, but its own workflow engine/dashboard overlap Captain's control-plane; only a narrow browser/knowledge adapter should be considered.
- Security/cost: real-session browser access and shell/git actions make permission scoping critical. Avoid enabling its scheduler/router-like features behind Captain by default.
- Decision: potentially useful browser subsystem, lower fit than a thin browser-control layer because of control-plane overlap.

## MCP OAuth authorization note
- Current official MCP SDK guidance treats Streamable HTTP MCP servers as OAuth 2.1 resource servers validating bearer tokens rather than inventing their own login/token issuance.
- Captain implication: OAuth connector setup should preserve official provider authorization flows and discovered authorization metadata; Settings must not silently synthesize credentials or downgrade auth.
