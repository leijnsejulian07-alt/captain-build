# Captain OSS scout — 2026-09-13

Scope: new or materially relevant components only. No third-party code was installed or executed.

## Strong candidates

### Omnigent — evaluate as adapter architecture reference, not a second control-plane
- Open-source meta-harness announced by Databricks in 2026; Apache 2.0 per the project announcement.
- Wraps heterogeneous coding agents behind a uniform session API and adds contextual policies, collaboration and sandbox-provider support.
- Captain fit: strong reference for backend adapter/session-policy boundaries and remote sandbox abstraction.
- Constraint: Captain must remain the single user-facing orchestrator and authority. Do not run Omnigent as a parallel router/daemon by default.
- Next: inspect repository/API surface and dependency/resource footprint before any integration experiment.

### OpenAI Symphony — orchestration pattern reference
- Open-source specification for issue-driven coding-agent orchestration.
- Useful patterns: persistent task ownership, isolated agent work, human review before landing, resumable work tied to external task state.
- Captain fit: borrow evaluation/task lifecycle ideas for persistent repo-aware jobs; avoid replacing Captain's existing router/task ownership model.

### Cursor SDK — optional coding backend candidate
- Cursor now exposes its coding-agent runtime/harness programmatically via a TypeScript SDK, locally or in Cursor-hosted execution.
- Captain fit: potentially useful optional backend behind the existing builder dispatch boundary, especially for repo-aware coding loops.
- Risks/constraints: external provider/auth/cost terms, TypeScript dependency, possible hosted paid execution. Must remain disabled until explicitly connected/enabled/ready in Captain Settings and must not silently consume paid capacity.
- Priority: below OpenBuilder and currently planned Freebuff/OpenCode work; evaluate only after local builder boundary is fully live and tested.

## Security/review direction

The current Captain fallback branch now includes a provider-neutral review/apply gate. It binds an external scanner result to an exact session-bound diff and requires both a clean finding count and explicit approval plus `diff_write` authority. This is intentionally scanner-agnostic so a mature scanner can be adapted later without embedding brittle credential heuristics into Captain.

## Decision

1. Keep OpenBuilder as baseline builder subsystem.
2. Finish Captain-native session/epoch/output/review/apply/rollback boundaries before adding another backend.
3. Evaluate Omnigent primarily for interface/policy design; do not stack it as a second orchestrator.
4. Treat Symphony as an orchestration/evaluation pattern source.
5. Park Cursor SDK as a later optional backend candidate subject to auth/cost/licensing/resource review.
