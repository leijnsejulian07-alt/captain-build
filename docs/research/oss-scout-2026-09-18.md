# Captain OSS scout — 2026-09-18

Parking-only research note while B310 is unreachable. No third-party code was installed or executed.

## Highest-value new patterns

### AWO (Agent Worktree Orchestrator)
Candidate: `ystepanoff/awo`.

Why it matters: the safety model is unusually aligned with Captain: deterministic verification exit codes are authoritative while agent self-reports are advisory; mutations are bounded to a configured worktree root; branch prefixes are constrained; dangerous permission/sandbox bypass flags are refused; protected paths and oversized diffs escalate instead of auto-landing.

Integration recommendation: **adapt patterns, do not adopt its control-plane**. Captain should keep ownership of `chat_id + project_id + repo_scope + epoch + builder_session_id` and map that authority to a bounded worktree lifecycle. Reuse the ideas of deterministic proof packs, protected-path escalation and explicit permission-required failures.

### Docker AI Sandboxes Git modes
Candidate: Docker's official AI Sandboxes Git workflow documentation.

Why it matters: it makes the isolation trade-offs explicit. Direct host mounts are poor for parallel Captain tasks. Clone mode offers stronger Git separation but needs explicit per-task branch/worktree discipline. Host-worktree mode isolates edits but intentionally prevents the sandbox from resolving host `.git`, which is attractive for a least-authority builder execution mode.

Integration recommendation: keep Captain's `SandboxProvider` abstraction and support capability profiles rather than one universal sandbox: e.g. `edit_only` (host worktree, no Git authority) and later `repo_agent` (isolated clone with narrowly scoped Git authority). Never silently upgrade capabilities.

### AQ workspaces
Candidate: AQ workspace lifecycle docs.

Why it matters: one task = one isolated worktree + branch + running session + lifecycle state. This is a clean UX reference for Captain's interactive builder pane and parallel project/chat isolation.

Integration recommendation: adopt the lifecycle concept, not another orchestrator. Captain remains the sole control-plane and persistent source of truth.

### Rove / Agetor / Daintree
These independently reinforce the same mature pattern: persistent agent sessions, isolated worktrees, diff/review surfaces, task status and reusable agent/skill presets. Rove additionally exposes recovery/handoff and a Doctor-style diagnostic surface; Agetor freezes a task's launch profile at first run, which is useful for reproducibility.

Integration recommendation: borrow UX and lifecycle patterns only unless a narrowly scoped adapter later proves cheaper and safe. Avoid stacking their routers/daemons beneath Captain.

## Concrete Captain acceptance requirements derived from scout

1. Builder/worktree authority must be bound to the exact Captain scope tuple and current Project State epoch; stale sessions fail closed.
2. Worktree creation/deletion must be constrained to a Captain-owned root and Captain-owned branch namespace.
3. Verification results come from captured command exit status/artifacts; model claims never mark tests green.
4. Protected paths, excessive diff size, permission escalation and sandbox-bypass requests become explicit review states.
5. Sandbox capability is explicit and immutable for a running builder session; no silent escalation from edit-only to Git/network/secrets authority.
6. Builder UI should expose files, diff, console/test evidence, preview, lifecycle state and rollback without making the underlying subsystem the user-facing orchestrator.
7. Session launch configuration should be snapshotted/fingerprinted so later Settings/plugin/model changes cannot silently mutate an already-running task.
