# Captain OSS capability audit — 2026-09-11

Purpose: identify genuinely useful new adapter/subsystem candidates without replacing Captain's single control-plane or weakening `chat_id + project_id + repo_scope + state_epoch` authority. No third-party code was installed or executed during this audit.

## OpenCode SDK / server — high-value Open Builder candidate

- Sources checked today: official OpenCode SDK and MCP/agent documentation plus `opencode-ai/opencode`.
- License: MIT for OpenCode.
- Capability: type-safe JS/TS SDK can create/control an OpenCode server programmatically; OpenCode already exposes coding-agent sessions, plan/build modes, permission controls, MCP integration and repo-aware tool use.
- Fit: stronger than embedding a second top-level agent UI. Captain can remain the user-facing orchestrator and authority while a narrow `OpenBuilderAdapter` owns only a scoped coding session. Captain should provide the authorized repo/worktree, canonical prompt context, explicit permissions and cancellation; OpenCode should return events/diffs/test output rather than owning Captain memory/routing.
- Resource/dependency cost: Node/server process plus model-provider calls. This is materially lighter than a full Docker/Kubernetes agent stack but still requires local benchmarking. MCP servers should stay disabled by default because OpenCode's own docs warn they can consume substantial context.
- Security: never forward Captain connector credentials wholesale; pass only capability-scoped handles or environment material explicitly approved for that builder session. Map OpenCode permissions to Captain's stricter policy rather than accepting permissive defaults.
- Decision: HIGH-PRIORITY CONTROLLED ADAPTER SPIKE after local reconciliation. Prefer SDK/server integration over shell-driving its interactive UI.

## microsandbox — promising sandbox backend, but Windows validation required

- Source: `superradcompany/microsandbox`.
- License: Apache-2.0.
- Capability: local-first microVMs for untrusted workloads, OCI-compatible images, Python/TypeScript/Rust/Go SDKs, detached long-running sandboxes, MCP support and no mandatory long-running daemon. Project currently advertises Windows support and hardware isolation.
- Fit: attractive future `SandboxAdapter` behind Open Builder because microVM isolation is stronger than merely trusting an agent process/container. It could isolate build/test/dev-server/browser workloads while Captain owns repo scope, epoch, permissions, lifecycle and UI.
- Important current risk: a Windows-specific startup regression was reported for v0.6.10+ in August 2026, with v0.6.9 working in the report. Therefore do not install or standardize on it until the user's laptop can benchmark a pinned known-good version and verify the current fix status.
- Secrets caveat: an open 2026 issue describes limitations around runtime-resolved store-backed secrets. Captain must not assume its vault semantics solve this automatically.
- Decision: PROMISING, NOT READY TO ADOPT. Run a disposable local benchmark/security spike only after the laptop returns; pin versions and keep credentials outside the guest.

## tank-agent-os — security architecture reference, not a laptop dependency

- Source: `np6126/tank-agent-os`.
- License: MIT; very small adoption footprint and single maintainer.
- Capability: immutable Fedora bootc + rootless Podman appliance, audited egress proxy, kernel nftables confinement, root-owned instructions and pinned agent/runtime artifacts.
- Fit: not appropriate as Captain's Windows desktop runtime, but its threat model is directly useful: containment must be enforced outside the agent, especially for untrusted repo/web content plus tool/network access.
- Useful patterns for Captain: explicit egress policy, immutable/root-owned policy layer, artifact pinning/checksums, audit logs and separation of persistent orchestrator from disposable execution environment.
- Decision: SECURITY REFERENCE ONLY; adapt principles into Captain sandbox acceptance criteria rather than importing the appliance.

## sandboxd — strong builder/preview reference, not a direct Windows default

- Sources checked today: upstream GitHub README/security/architecture surface and current project documentation.
- License: MIT. Upstream currently shows active development and a deliberately API-first Go control plane around Docker, Traefik and SQLite.
- Capability: isolated per-app containers, live preview URLs, files/editor, logs, git diffs, snapshots/fork/restore, checkpointed tasks and OpenCode/Claude Code adapters. Its API-first design means useful pieces could sit behind Captain without exposing sandboxd's own console as the primary UX.
- Fit: particularly relevant to Captain's builder pane and plan→build→preview→diff→rollback lifecycle. Prefer borrowing or adapting its preview/snapshot/task patterns rather than importing its complete control plane, because Captain must stay authoritative for routing, memory, permissions and project epochs.
- Security/resource caveat: upstream explicitly describes container rather than VM isolation, single-server assumptions and API auth that is off by default in its beta configuration. The documented quick start targets Linux Docker; Windows is not presented as a primary supported host path. Do not install on the user's laptop without a separate compatibility/threat-model review.
- Decision: HIGH-VALUE DESIGN/ADAPTER REFERENCE. Consider narrow reuse of preview/snapshot interfaces if they can be isolated behind Captain; do not make it Captain's second orchestrator.

## Limboo — highly relevant local-first workspace architecture reference

- Source checked today: `limboo-ai/limboo` upstream documentation/README.
- License: MIT. Current implementation is Electron + React + TypeScript with Windows packaging support.
- Capability: provider-neutral agent adapters, repo/worktree/session lifecycle, terminal/file watching, durable project memory, search, permission handling and a local-first security boundary. Provider authentication remains with each underlying agent rather than being copied into the workspace.
- Fit: unusually close to Captain's desired separation of concerns: one workspace/control layer above interchangeable coding agents. Its adapter seam, permission unification, worktree handling and provider-neutral timeline are useful architectural references for Open Builder and GitHub/repo-aware workflows.
- Resource/dependency cost: Electron plus native modules (`better-sqlite3`, `node-pty`) is non-trivial on a laptop; wholesale adoption would also duplicate Captain's UI/workspace/control plane.
- Decision: ARCHITECTURE/IMPLEMENTATION REFERENCE, NOT WHOLESALE INTEGRATION. Inspect narrow reusable patterns/components only after license/dependency/security review; Captain remains the single control plane.
