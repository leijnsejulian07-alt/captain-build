# Captain OSS capability audit — 2026-09-10

Purpose: identify reusable components/patterns that improve Captain without replacing its single control-plane or weakening `chat_id + project_id + repo_scope + state_epoch` authority. No third-party code was installed or executed during this audit.

## HyprDesk

- Source: https://github.com/HyprDesk/hyprdesk
- License: MIT.
- Capability: desktop orchestration of coding agents with git-worktree isolation, persistent sessions, PTY-driven agents and a Tauri v2 IDE surface.
- Fit: useful reference for Captain's builder pane, especially worktree/session UX and merge-back. Captain must retain routing, authority, memory and permission ownership; do not import its router-leader as a second control-plane.
- Risk/cost: very young project and low adoption; real PTYs/agents mean green typechecks alone are insufficient. Treat as design reference first, not trusted runtime dependency.
- Decision: WATCH / ADAPT PATTERNS, not direct integration yet.

## devsandbox

- Source: https://github.com/zekker6/devsandbox
- Capability: per-project agent sandboxing; protects SSH/cloud credentials, `.env` files and sibling projects; supports worktree isolation and network logging/filtering.
- Fit: strong candidate to study behind a future backend-neutral `SandboxAdapter`, because its security boundary addresses exactly the class of builder/agent leakage Captain must prevent.
- Platform/resource note: bubblewrap on Linux, Docker or libkrun elsewhere. Windows laptop suitability and resource cost require local benchmarking before adoption.
- Decision: EVALUATE ADAPTER FIT; never blindly install or execute. Verify license/security/dependency posture before any integration.

## MCP Tasks Extension / 2026 direction

- Official source: https://tasks.extensions.modelcontextprotocol.io/seps/2663-tasks-extension
- Tasks are an official extension with `tasks/get`, `tasks/update`, and `tasks/cancel`; task creation is per-request/server-directed.
- The old unscoped `tasks/list` was removed because it could not be scoped safely in the stateless model.
- Fit: validates Captain's fail-closed scoped-job direction. If Captain exposes MCP-compatible async jobs, ownership must remain Captain-controlled and project/epoch-bound rather than adding a globally enumerable task plane.
- Decision: ALIGN SEMANTICS where useful; do not replace Captain's persistent job store/control-plane.

## OpenHands Agent SDK / Canvas — fresh evaluation

- Sources: `OpenHands/OpenHands` and `OpenHands/software-agent-sdk`; upstream activity was current through 2026-09-09 in today's check.
- License/maintenance: core and software-agent SDK are MIT; enterprise-only pieces have separate licensing and are excluded from Captain integration plans.
- Capability: active Agent Canvas, Agent Server/SDK, TypeScript client, workspaces/events and repo-aware coding-agent architecture.
- Fit: strong candidate for a narrow Open Builder backend adapter or architecture reference. Captain must remain the sole router, memory authority and user-facing orchestrator; do not import OpenHands automation as a competing control-plane.
- Resource/security: container or remote backends can be expensive on a laptop. Benchmark RAM/CPU/startup cost and enforce Captain project/repo/epoch boundaries before enabling any runtime adapter.
- Decision: HIGH-PRIORITY CONTROLLED SPIKE after local reconciliation of the current authority/settings work.

## Nightona / Daytona continuation — fresh evaluation

- Source: `nightona-co/nightona`.
- License/status: AGPL-3.0 continuation of Daytona's last open v0.190.0 after Daytona moved core development private in June 2026. Nightona describes itself as still in bootstrap/rebrand phase.
- Fit: sandbox/workspace concepts are relevant, but AGPL obligations, bootstrap maturity and Docker/Kubernetes resource cost reduce direct laptop fit.
- Decision: WATCH ONLY. Do not integrate until maintenance/security maturity and licensing implications are re-evaluated.

## MCP authorization 2026-07-28 — fresh architecture input

- Official MCP sources checked today confirm issuer validation, credentials bound to their issuing authorization server, and Dynamic Client Registration deprecation in favor of Client ID Metadata Documents.
- Fit: reinforces Captain's canonical Settings + provider-adapter design: never invent auth, track auth-method/version migrations, use official Connect flows, and keep credential material outside Captain's persistent lifecycle/event state.
- Decision: treat these as connector acceptance criteria, especially for future MCP/OAuth adapters.

## Community signal: self-hosted agent control centers

- Recent Reddit/self-hosted discussion around Codeman and OpenHands-style control centers emphasizes persistent sessions, browser-visible terminals and per-project containers.
- Community feedback specifically calls for per-agent/folder/tool permissions, logs and a kill switch rather than one giant permission bucket.
- Fit: supports Captain's existing builder-pane direction: visible session ownership, scoped permissions, explicit stop controls, observability and rollback.
- Decision: use as UX/security input only; no direct dependency without repository/license/security review.

1. Finish local reconciliation of canonical `ProjectAuthority` + memory/builder stores when the laptop returns.

3. Then run a controlled OpenHands SDK adapter spike behind Open Builder and benchmark laptop cost.
