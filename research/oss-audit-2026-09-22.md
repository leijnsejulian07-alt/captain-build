# Captain OSS capability audit — 2026-09-22

Scope: candidates that can sit behind Captain's single control-plane. No candidate was installed or executed. Treat all third-party code as untrusted until pinned, reviewed, sandboxed and locally verified.

## High-value candidates

### Rivet sandbox-agent
- Role: adapter for controlling existing coding agents (Codex, Claude Code, OpenCode, Amp/Pi) over HTTP inside a sandbox.
- Fit: high as a builder-worker adapter behind Captain; it does not need to replace Captain routing or Project State.
- Resource profile: Rust/static-binary design is attractive for a laptop-hosted control plane, while actual execution should remain isolated.
- Security caveat: documentation includes credential extraction/injection workflows. Captain must not copy this blindly; credentials must remain explicit, scoped and never persisted in project memory/logs.
- Integration rule: Captain owns chat_id + project_id + repo_scope + state_epoch; every sandbox session must carry that authority tuple and fail closed on mismatch.
- Decision: promising; adapter prototype only after local review and license/dependency verification.

### Ephemeral Sandbox
- Role: isolated workspaces for parallel coding agents with reviewable publication, observability, CLI/MCP.
- Fit: strong conceptual match for builder-session/repo isolation and atomic review/publish.
- Resource profile: Rust core is promising, but daemon/runtime footprint and Windows/laptop ergonomics need measurement.
- Integration rule: use as execution substrate only; never introduce a second Captain control-plane. Workspace/session IDs must be subordinate to Captain Project State epoch.
- Decision: promising architecture reference / possible subsystem; benchmark locally before adoption.

### Omnigent
- Role: open-source meta-harness around multiple coding agents with common session API, contextual policies and collaboration.
- Fit: some useful adapter/policy ideas, but adopting the whole meta-harness risks duplicating Captain's primary router/control-plane.
- Decision: do not adopt wholesale. Mine interoperable session/policy patterns only unless a narrow adapter can be isolated.

### Hazmat / Nono-style local containment
- Role: constrain local coding agents away from developer credentials/home directories; Nono-style per-tool scoped authority is especially relevant.
- Fit: high security value for local builder execution.
- Decision: research further; prefer OS-enforced least privilege over prompt-only policy. Do not install until Windows compatibility, license, maintenance and bypass resistance are verified.

## Explicit rejection / caution

### DeepSeek Harness
A recently reported sandbox-escape issue makes it unsuitable for blind integration. Even if patched, require a fresh security review before reconsideration.

## Captain design consequences
1. Keep Captain as the sole user-facing orchestrator and authority source.
2. Builder adapters receive a short-lived capability envelope derived from chat_id/project_id/repo_scope/state_epoch; no adapter may widen it.
3. Sandbox/provider session state is cache/worker state, not persistent truth. Captain Project Memory remains source of truth.
4. Publication back to a repo requires epoch revalidation plus a reviewable diff; stale sessions cannot publish.
5. Credentials are connector-owned, explicit and scoped; never serialize secrets into Project Memory, task payloads, provenance records or UI notices.
6. Prefer a thin adapter boundary so Rivet/Ephemeral/other workers can be swapped without changing Captain routing.
