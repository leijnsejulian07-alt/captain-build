# Captain OSS audit — 2026-09-23

## Scope
Daily scan focused on memory/context subsystems that could improve Captain without becoming a second control-plane. No third-party code was installed or executed.

## Candidates

### Letta
- Active stateful-agent/memory platform; Apache-2.0 according to upstream GitHub metadata.
- Strong ideas: explicit core/recall/archival memory tiers, model-agnostic runtime, self-hosting.
- Integration concern: Letta is itself an agent runtime/control-plane. Running it wholesale behind Captain risks duplicate routing, state ownership and persistence semantics.
- Decision: **ideas/adapters only for now**, not a second daemon. Consider borrowing memory-tier semantics or using a narrowly bounded storage adapter only after Captain's epoch authority wall is locally green.

### Mem0 family
- Mature universal memory approach with multi-signal retrieval and recent evaluation work.
- Integration concern: hosted defaults/API-key paths and memory identity semantics must never bypass Captain's project authority tuple.
- Decision: **candidate adapter, not source of truth**. Any experiment must inject and verify `chat_id + project_id + repo_scope_hash + state_epoch` on every write/read/delete and disable implicit global/user memory for project facts.

### GroundMemory
- Local-first, MCP-native, human-readable memory; attractive laptop/resource profile on paper.
- Less mature than Letta/Mem0 and upstream claims require independent validation.
- Decision: **watchlist / prototype candidate**, only in an isolated benchmark fixture; do not install into Captain runtime yet.

### OpenHands / agent-control-center direction
- Community feedback reinforces a key Captain requirement: a single dashboard must not become a single giant permission bucket; per-agent/folder/tool boundaries and kill controls matter.
- Decision: retain OpenHands as a builder-subsystem candidate, never as Captain's authority/memory owner.

## New architectural requirement
A third-party memory adapter is acceptable only if Captain remains the persistent authority. Adapter API must be capability-scoped and epoch-bound:

`MemoryAuthority = { chat_id, project_id, repo_scope_hash, state_epoch }`

Rules:
1. Project memory reads/writes require exact equality on all four fields and `state_epoch >= 1`.
2. No adapter-generated user/global namespace may contain project-specific facts.
3. Epoch transition makes prior-epoch records inaccessible immediately; physical cleanup may be asynchronous but cannot restore visibility.
4. Non-project chat uses a separate explicit namespace and must never infer/project an authority tuple.
5. Adapter metadata may store hashed repo scope, never raw local paths or secrets.
6. Import/export must preserve provenance and authority; unknown/missing authority fails closed.
7. Captain owns summarization/distillation policy. Shared distilled learning is allowed only after a classifier proves it is non-project-specific.
8. No network/paid provider is enabled implicitly. Settings must expose install/connect/enable/ready/permissions separately.

## Evaluation gate before integration
Build a provider-neutral memory conformance suite first. Run the same fixture against Captain-native memory and any candidate adapter: same-epoch retrieval succeeds; changed epoch/project/chat/repo hash returns zero records; malformed authority fails closed; normal non-project chat still works; delete/tombstone cannot cross authority walls; provenance survives round-trip; no secret/raw-path fields appear in logs or serialized notices.

## Priority
Do **not** replace Captain memory yet. Highest value remains local implementation of the P0 Project Memory/context epoch wall. Once that is green, use this conformance suite to compare a native implementation against one local-first candidate before adopting any dependency.
